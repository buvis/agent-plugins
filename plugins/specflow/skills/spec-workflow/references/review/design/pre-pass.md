# Design pre-pass

Loaded at every tier. The adversarial pass a draft gets inside the design review, before its findings are walked. It is one review with a pre-pass, not a second review and not a separate log.

- [SR-RVD-114] Before walking a draft's findings, run an adversarial pre-pass within this same review: an isolated reviewer where the host can run an isolated sub-task, else an inline critique of your own that ends in a written summary. A host without isolation is not a reason to skip the pass. A design already approved and reviewed again gets no pre-pass; its walkthrough starts from the current findings.
- [SR-RVD-115] The reviewer receives one self-contained package and nothing else: the current text of `design.md`, a summary of the approved requirements artifact (in Design-First, a summary of the intake item), and the full text of `cardinal-sins.md` with the severity definitions below. It returns findings only, each as `{severity: cardinal-sin|blocker|non-blocker|question, title, evidence, suggested_fix}`, anchored to a design section or a `file:symbol`; it edits nothing and approves nothing. A finding with no anchor is dropped, since it cannot be walked.
- [SR-RVD-116] The severities: a cardinal sin is an item of `cardinal-sins.md`, a blocker regardless of justification; a blocker makes the design wrong or unbuildable as written; a non-blocker is a real concern the task planning can proceed with; a question is an ambiguity a reader could misread. Calibrate: an ordinary concern inflated to a blocker dilutes the signal, so ask whether the design is wrong without the fix.
- [SR-RVD-117] The author applies the fix for each cardinal sin and blocker it can resolve from the requirements and the repository, under the check before a write, and records each fix as a minutes line in the intake item's `qa-log.md` under `## Review: design.md <date>` (severity, title, "fixed by the author", resolved). A fix that needs the developer's decision (a missing owner, an unstated budget) is not invented: the finding stays open for the walkthrough. When at least one such fix was made, run one verification pass with the same package on the updated draft; never a second one, and never a loop.
- [SR-RVD-118] After the verification pass, each blocker still open goes to the developer in the walkthrough first, and the design approval is refused while one stays open and undisputed. The non-blockers and questions enter the walkthrough too, each chosen edit landing before the next card as the core says.
- [SR-RVD-119] The recap of the design review states the number of passes run (one or two), the findings by severity, the fixes the author applied, the blockers still open, and the concerns and questions still unresolved. It records no approval; the approval summary of the shared dialogue rules follows it. Cross-model review is optional through what the host offers: no named model, external command, pinned output line, minimum finding count, or exit code is required.
