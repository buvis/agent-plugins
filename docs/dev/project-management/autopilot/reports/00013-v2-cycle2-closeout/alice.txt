### Open item 1: parent-alias helper finding (adjudicated)

The audit's claim is correct at this HEAD, and it has a runtime consequence beyond the helper-only probe.

- `_pinned_parent_fd` falls back to `parent.resolve().relative_to(root.resolve())` when the path is not spelled under `root` (log_sink_refusal.py:191-195). That removes below-root symlink components before the `O_NOFOLLOW` descent.
- The preflight is meant to catch this, but the `_symlinked_component` stop rule `if not parent_inside and is_root: break` (log_sink_refusal.py:157) misses it. The rule breaks on any component that resolves to the root while its parent resolves outside it. A path that leaves the repo through a committed symlink and returns through a symlink to the repo root is therefore never walked. The docstring claims it handles "one that leaves the repository and returns".
- I reproduced this in scratch. Setup: repo containing a committed `out -> /elsewhere`, and `/elsewhere/back -> repo`. Log path: `repo/out/back/logs/x.log`.
  - `_symlinked_component` returns False in both the same-spelling and the aliased-root cases.
  - `run_verification` with the repo spelled directly returns `sink-failed`. The open's `O_NOFOLLOW` catches it, but with the wrong error slug and not `unsafe-artifact-path`.
  - `run_verification` with the root spelled through a symlink alias returns **`ok: True`**, and the log is written through both symlinks to `repo/logs/x.log`.
  - A tracked target (`repo/out/back/README.md`) is still refused with `unsafe-artifact-path`, and the file is untouched. I saw no outside-root or tracked-file overwrite.
- The existing R-D1 test (test_helper_rework_sinks.py:643) only returns to `real/logs`, never to the root, so it misses this.
- Scope of the runtime consequence: a symlinked component is accepted when the root and the output are spelled differently. The write lands at a location `refuse` already judged on the resolved path. The broader "tracked-file overwrite / `run_verification` bypass" hypothesis stays UNVERIFIED and is not supported by my probes. No defect-closure or clean-delivery claim is warranted.

### Open item 2: `subprocess.run(timeout=60)` in the staging probe (verified and classified)

- It is verified. This is the only call in review_stage.py that can raise `subprocess.TimeoutExpired`.
- `stage_review` has no handler for it. The CLI's `_call` (autopilot.py:127-131) catches only `TypeError` and `ValueError`. A Git hang therefore ends in a traceback after 60 seconds, not a refusal report. Other `_git` calls (dirty_tree.py:19) have no timeout.
- It fails closed by crashing, with no silent grant, so it is not a safety hole. It is an inconsistency with the function's own "every other failure fails closed" contract.
- Classification: a Medium contract inconsistency, not an established failure. No test covers it.
