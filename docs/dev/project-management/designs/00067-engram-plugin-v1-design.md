# Design: Engram plugin — recall skill, MCP server, per-host nudge hooks

## Architecture fit

This repo is a monorepo of independently-distributable Agent Plugins
(`AGENTS.md` § Structure): each immediate child of `plugins/` is one plugin
root, validated by `scripts/validate.py`. `plugins/autopilot/` is the closest
existing reference for root-manifest shape (`name`, `version`, `description`,
`author`, `license`) and for client-extension packaging under per-host
directories (`com.anthropic.claude-code/`, etc., named by the
`extensions` object the validator checks at `scripts/validate.py:144-149`).
`templates/example-plugin/` confirms the minimal root manifest shape with no
extensions. This PRD is a pure configuration/skill package — no executable
Python ships in `plugins/engram/`; the `engram` CLI itself lives in the
separate `buvis/engram` repo and is assumed present on PATH (the PRD's
`eligibility` gate: `engram nudge --help`).

The new plugin lands as `plugins/engram/`, a sibling of `plugins/autopilot/`
and `plugins/specflow/`, following the same root-manifest + per-host-extension
pattern. Nothing in the existing repo structure needs to change to accommodate
it; this is an additive package.

  the `autopilot` job's own test only asserts a pytest step is present among
  others via `any(...)`, so one more named step there is additive and safe).

### `plugins/engram/works.earendil.pi/engram-nudge.ts`

Default-export a function taking `pi`. On `tool_result`, return unless
`isBashToolResult(event)`; run `engram nudge plain` with stdin
`JSON.stringify({tool_input: event.input, cwd: ctx.cwd})` and a 12-second
timeout; when stdout is non-empty, return
`{content: [...event.content, {type: "text", text}]}`.

```typescript
import { isBashToolResult } from "@earendil-works/pi-coding-agent";

export default function (pi: ExtensionAPI) {
  pi.on("tool_result", async (event, ctx) => {
    if (!isBashToolResult(event)) return;
    const text = await runEngramNudgePlain(
      JSON.stringify({tool_input: event.input, cwd: ctx.cwd}),
      12_000,
    );
    if (text) {
      return {content: [...event.content, {type: "text", text}]};
    }
  });
}
```

(`isBashToolResult` is a real export of `@earendil-works/pi-coding-agent`
(`.../pi-coding-agent/docs/extensions.md`), imported, not a local helper — the
PRD's "Not run in the spike" caveat is about never exercising this adapter
live, not about inventing its API. `ExtensionAPI` is the package's own
extension-context type; `runEngramNudgePlain` is the one implementation-local
helper this file defines itself: spawn `engram nudge plain`, write the JSON
string to its stdin, capture stdout, enforce the 12 s timeout, and return the
stdout text (or empty). The PRD marks this file untested — no test depends on
its exact internals, only that it exists and is referenced from
`plugin.json`'s `extensions`.)

## Data flow

Pull path: a host loads `plugins/engram/skills/recall-prior-work/SKILL.md` at
session start (or on-demand per its skill-loading convention); when the agent
decides a broad search is warranted, it runs `engram query` itself via Bash —
no code in this plugin executes that query, the skill text is the only
artifact.

Push path: a host's own hook runner fires `PostToolUse` after a Bash tool
call, matched to `Bash`; it shells out to `engram nudge <host>`, which reads
the tool call's own context (host-specific — Claude Code and Codex pass
nothing on stdin per their hook contract, Copilot CLI's hook contract is
unread beyond the command shape, Pi's extension builds and passes a JSON
stdin payload itself) and prints context-injection text to stdout, which the
host's hook mechanism surfaces back into the agent's context. `engram nudge`
itself (the decision of whether the prior search was broad enough to warrant
a nudge) is entirely owned by the `engram` CLI in the sibling `buvis/engram`
repo — out of this PRD's scope by design (Companions note in the PRD header).

No data crosses from this plugin's own files at runtime beyond the exact
command strings and MCP registration shown above; there is no plugin-owned
runtime state.

## Reuse inventory

Searched before designing any new file:

- `rg -n "extensions" plugins/*/plugin.json` → only `plugins/autopilot/`
  defines per-host extension directories (`com.anthropic.claude-code/`,
  `com.openai.codex/`, etc. — confirmed by reading
  `plugins/autopilot/plugin.json`); its shape is reused verbatim for
  `com.anthropic.claude-code`, `com.openai.codex`, `com.github.copilot` above.
- `rg -n "PostToolUse" plugins/` → no existing `hooks.json` in this repo
  (autopilot's host execution lives behind compatibility packages not yet
  shipped per its manifest description "execution is unavailable pending host
  certification"); nothing to copy byte-for-byte, so the hook shape above is
  authored fresh from the PRD's literal content.
- `rg -n "mcpServers" plugins/ --glob '*.json'` → no existing `mcp.json` in
  this repo to copy from; confirmed against `scripts/validate.py:432`'s
  `mcp.json` check, which only validates shape, not content, so there is no
  existing convention beyond the schema URL already used by
  `plugins/autopilot` for its own `$schema` fields (verified:
  `rg -n "agent-plugins.org/schemas" plugins/autopilot/*.json`).
- `rg -n "recall" plugins/ tests/` and `rg -n "nudge" plugins/ tests/` →
  nothing found (proven against a known-present term `rg -n "name" plugins/*/plugin.json`,
  which returns every manifest, so the empty `recall`/`nudge` result is a
  true absence, not a broken search).
- `ls tests/` → `tests/autopilot/`, `tests/specflow/` exist with their own
  `__init__.py`; `tests/engram/` follows the same per-plugin test directory
  convention, matching `AGENTS.md`'s "Keep lockfiles and distributable plugin
  assets tracked" boundary (tests never ship inside `plugins/<name>/`, per the
  specflow precedent cited in the project capsule's Key Invariants: "Shipped
  code under `plugins/specflow/` ... Tests live in `tests/specflow/`, never in
  the package").

## Alternatives considered

1. **Smallest-diff: skill + MCP only, no host hooks** (the "Portable pull
   path" capability alone). Rejected as too small: the PRD's own Problem
   Statement is that agents don't self-initiate (14/364 sessions), so a
   pull-only package repeats the status quo. The PRD explicitly scopes in the
   push path as a companion capability; this option is listed to show the
   floor, not chosen.
2. **One generic `hooks.json` reused across hosts via symlinks** instead of
   four separate per-host files. Rejected: Claude Code, Codex, and Copilot CLI
   each use a different hook-file schema (`PostToolUse`/matcher shape vs
   `postToolUse`/`bash` key vs timeout field name `timeout` vs `timeoutSec`),
   so a shared file would need host-conditional parsing the hosts themselves
   don't do. Four small literal files are simpler and match the PRD's exact
   per-host Behavior bullets.
3. **Chosen: four independent per-host extension directories + one shared
   skill + one shared `mcp.json`**, exactly as the PRD specifies. This is the
   design actually written above. The extra size over option 1 buys the push
   path the Problem Statement asks for; the per-host duplication over option 2
   buys correctness against three incompatible hook schemas without any
   runtime indirection.

## Risks & edge cases

- **The path-valued Claude `hooks` field is a guess** (PRD Risks, carried
  forward unchanged): every other installed buvis plugin uses the default
  `hooks/hooks.json` location, not a path override. If Claude Code ignores the
  override, the fix is a file move (`com.anthropic.claude-code/hooks.json` →
  `hooks/hooks.json`) plus a README note — no interface change, so it does not
  block this design.
- **Likely next change 1**: a Kiro hook adapter, once its hook file schema is
  read (explicit non-goal here). This design's `extensions` object already
  has room for a `com.kirodev.kiro` (or similar) key without restructuring.
- **Likely next change 2**: a Gemini CLI adapter, blocked today only by local
  auth, not by any shape decision — same extension-object slot pattern
  applies.
- **Likely next change 3**: wiring `ENGRAM_PACK_FILE`/`ENGRAM_NUDGE=off` from
  the orchestrator work in intake 00066, which this PRD's Companions note
  flags as sharing "the two environment guards" — this design does not set
  those variables itself, only documents them in the README, so 00066 can set
  them from outside without touching this plugin's files.
- **Edge case**: a hook command string gets a path prepended by a future edit
  (e.g. `${CLAUDE_PLUGIN_ROOT}/bin/engram nudge claude`) — caught by
  `test_every_hook_command_is_bare_engram_nudge` and the Success Metric's
  "no shipped file names a path inside the plugin" check.

## Test strategy outline

- **Package validator**: `python3 scripts/validate.py plugins/engram` must
  exit 0 after Phase 0 — covers manifest shape, `extensions` object shape,
  `mcp.json` shape per the existing validator rules (no new validator code
  needed; this package exercises existing rules only).
- **Contract tests** (`tests/engram/test_package.py`, Phase 1): the five named
  tests above, each asserting one Behavior bullet from the PRD. Written after
  Phase 0's files exist, so each test can assert against real file content
  rather than a stub.
- **Integration step** (Phase 2): `.github/workflows/validate.yml` gets the
  `tests/engram` discovery step in the `autopilot` job; `python3
  scripts/generate_marketplace.py --check` must exit 0 after the regen; `rg
  -c "tests/engram" .github/workflows/validate.yml` must print at least 1;
  `python3 -m pytest tests/autopilot -q` must still pass (confirms the new
  step did not land in the `plugins` job's pinned list).
- **No live host verification in this PRD**: the README's status table
  carries forward the spike's own verification claims (`verified
  2026-11-10` for Claude Code/Codex/Copilot CLI, `untested` for Pi) rather than
  re-verifying live in this build — this PRD is a transcription of the spike's
  proven content, not a new live-verification pass.
